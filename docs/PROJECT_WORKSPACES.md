# 项目、本地工程与无限画布方案

2026-09-24。状态：用户已授权并实现本地项目基础；无限画布交互及 Git 操作仍为后续范围。下方保留整体设计，已交付内容以本节为准。

## 已实现：项目基础

顶部「项目」入口提供新建、路径打开、最近项目；新建自动进入「首页」。项目内可以添加、切换、复制页面，历史页面可显式复制进项目。原有公共页面与历史不迁移、不删除。项目管理标准控件使用绑定组件库的 C-02/C-21、Foundation 与图标。

实际文件结构：根目录 `page-builder.project.json` 保存 schemaVersion/projectId/name/defaultCanvasId/创建时组件库绑定；`.page-builder/pages/*.json` 为页面事实；`canvases/main.json` 预留默认画布及 placements，页面成员直接来源于 pages 目录，不维护第二份引用列表；`libraries/<snapshotId>/manifest.json` 及资源为可移植组件快照，manifest 已含完整 digest，因此此增量不重复生成 library-lock.json；`local/` 为 Git 忽略的历史、选区、锁。无限画布位置与交互尚未实现。

`ProjectManager` 通过真实目录路径生成本机 workspaceId，全局索引只登记目录与访问时间。每次 HTTP/MCP 请求独立解析存储，绝不修改进程共享的“当前项目”。同一 projectId/pageId 的两个目录副本拥有不同 workspaceId。AI 组件附件和页面工具结果带 workspaceId，截图 URL 同样带工作区范围。

创建先准备页面和快照，最后发布项目清单；同名目录直接拒绝，失败清理自己创建的未完成目录。页面保存前先确保对应资源快照已经发布；多页成员直接枚举已完成的页面文件，因此没有“已引用但页面不存在”的中间状态。快照导出原子发布、源路径脱敏；打开核对页面格式及全部资源 digest，缓存存在也不跳过工程资源完整性检查。新页面默认使用项目创建时绑定，手动刷新仅改变明确目标页面，不静默改变其他项目。

切换前完成原位保存、等待队列并阻止未应用属性草稿离开，切换后清除旧 AI 引用；轮询响应携带本地切换 epoch，旧项目响应不得覆盖新项目。跨库切换沿用原生资源重载。不同源网页不能调用本地项目 API。

限制：当前输入文件夹完整路径，没有系统目录选择器；不能将普通源码仓库逆向转换为页面；外部 Git/编辑器与搭建器并发写入尚未实现内容摘要令牌保护，请结束当前编辑后操作 Git 并重新打开。页面仍按 expectedRevision 防止搭建器进程之间的过期写入。测试与证据见 [验收](ACCEPTANCE.md)。

## 层级与用户操作

- 项目对应一个本地文件夹，可关联一个 Git 仓库；入口提供新建项目、打开本地项目、从 GitHub 克隆、最近项目。
- 首版建议每项目一个默认无限画布，数据结构保留 canvasId，以后可扩展多个画布。
- 画布支持平移、围绕鼠标缩放、适应全部页面、回到当前页面；页面以画板预览展示名称和尺寸，可创建、重命名、复制、摆放。
- 单击选择页面，右侧展示页面信息；双击进入现有页面编辑器，返回画布保留原视角。画布模式移动页面画板，页面模式拖动内部组件，明确区分两种操作。
- 画板位置属于画布坐标；页面内部布局与输出尺寸属于页面。移动画板不能改变页面内容或页面 revision。
- 标准 UI、图标与 Foundation 沿用当前组件库，画布几何/视口交互由编辑器负责。组件库保持独立，仍由用户手动刷新。

## 初始代码依据（项目增量前）

- `plugins/page-builder/src/server.ts` 将一个 PageStore 绑定到全局 `~/.codex/page-builder/v1/pages`；当前没有 ProjectStore 或项目目录切换。
- `src/store.ts` 的 FilePersistence 已可注入目录，并提供页面 JSON、跨进程锁、原子文件替换和按版本分离的历史/选区，可以复用。
- `src/domain.ts` PageSchema 严格校验现有字段，没有 projectId/canvasId；项目归属应先在外层建立，不随意给旧 Schema 添加未知字段。
- `src/server.ts` / `src/http.ts` / UI 路由目前以 pageId 为主；项目级操作与 AI 上下文必须补充工程身份。
- 当前页面绑定组件库内容快照，但资源实际位于本机库缓存；只有页面 JSON 和 snapshotId 无法保证另一台电脑还原。现有 exportPage 会打包固定运行资源，可借鉴其资源收集和去除本机 sourcePath 的处理。

## 建议的本地工程格式

```text
我的项目/
  page-builder.project.json         # 格式版本、项目 ID、名称、默认画布
  .page-builder/
    canvases/main.json             # 画板的 pageId、x/y、展示尺寸、顺序、revision
    pages/<pageId>.json             # 现有页面 Schema，稳定 ID，单页单文件
    library-lock.json              # 页面使用的组件库版本、完整 digest、相对资源位置
    libraries/<digest>/...         # 可复现的组件运行资源快照
    assets/...                     # 项目素材，使用工程相对路径
    local/...                      # 本机视角、历史、选区、锁、预览缓存；Git 忽略
  src/...                          # 项目已有业务代码，可选
```

工程目录是持久化事实来源；全局索引只保存“最近打开路径”。项目文件和页面数据可 Git 管理，本机临时状态不提交。第一版随工程携带所需不可变运行快照，以体积换取克隆后可复现；后续有稳定包分发时再改为按锁文件恢复依赖。快照是组件库的消费产物，不将组件源实现并入插件。

项目 ID 稳定；同一仓库在两个本地目录的副本必须有不同的本机 workspace handle。查询与写入使用 workspace + projectId + pageId，避免同 ID 的多个检出互相写错。持久文件和 Git 中不存电脑绝对路径或凭据。

## GitHub 使用边界

- 克隆先落到选定的本地目录，成功后验证工程清单、页面与库依赖，再打开；失败不登记成可用项目。
- 已含搭建器项目格式的仓库可以恢复页面和画布。普通 React/Vue/HTML 仓库可作为工程目录并添加搭建器数据，不能承诺自动将任意源代码转换为可拖拽页面；代码逆向适配属于独立功能。
- 编辑自动保存到本地文件，Git 提交/推送与保存分开。首版建议支持手动克隆与手动拉取，提交/推送先沿用开发工具；不增加后台自动同步。
- 手动拉取前检查未提交改动，仅允许可安全前进的更新；脏工作区或冲突保留现场并提示处理，不用 reset/clean 或自动覆盖。拉取前收束当前编辑，拉取后重新校验依赖并使旧编辑会话失效。
- 页面 revision 只保护本地操作，不能代替 Git 内容身份。外部编辑/分支切换可能带来相同 revision 的不同内容，因此写入还需核对读取时内容摘要，或显式重开工程并作废旧操作令牌。

## 模块划分与性能

ProjectStore 管项目索引和清单；CanvasStore 管画板排列；已有 PageStore 管组件树；RepositoryService 管 Git；组件库管理器解析项目锁定资源。UI、HTTP 和 MCP 调用相同领域操作，所有入口明确工程身份。

画布布局修改有独立版本与撤销记录；页面修改沿用现有原子操作。创建/复制页面与建立画板引用跨文件，需有工程事务或可恢复日志，失败不能出现缺页引用。缩放/平移只更新本机视角，拖动画板结束时才提交位置。删除第一版使用可恢复机制。

无限画布以虚拟坐标实现，不创建超大位图。概览使用按页面 revision 和库 digest 缓存的预览，只绘制可见画板；进入单页时挂载真实编辑器。页面数量增长时，不为每一页同时常驻一个完整 Renderer/iframe。AI 默认读取项目摘要和被明确引用的页面/组件，避免把整个项目塞进每条上下文。

## 实施顺序与验收

1. 项目基础：新建、打开、最近项目、文件夹持久化、页面创建/复制/切换；兼容旧页面。旧全局页面作为“历史页面”只读来源，可显式导入项目，导入成功前保留原文件与历史。
2. 无限画布：平移/缩放/画板摆放/适应全部/进入单页和返回视角；验证移动画板不改变内部页面，重开恢复，窄面板可用，多页只加载可见预览。
3. GitHub：克隆、恢复库资源、手动安全拉取；验证在无原机缓存的隔离目录能打开同样页面；鉴权失败、依赖缺失和 Git 冲突不得显示假成功。
4. 联合验收：两个项目或仓库副本含相同 pageId 时互不串写；快速切页和晚到保存不串页；未保存原位草稿切项目时被正确处理；跨文件写入中断恢复；外部修改和 Git 切换后拒绝过期操作；原有组件编辑/上下文/导出回归。

工作量主要在多项目上下文隔离、无限画布性能、跨电脑资源复现和 Git 后的状态恢复。创建项目对话框本身较简单。建议分可运行增量实施，不将方案记录算作实现通过。

## GitHub 插件复用选项（2026-09-24）

用户提出直接复用 GitHub 插件。核对本会话工具定义，已有仓库/文件读取、分支、远端提交对象和 PR 等能力，没有发现本地 clone/checkout/pull 的 GitHub 工具；这项核对不代表已经实测账号授权或执行仓库操作。

推荐首版分工：
- 搭建器实现本地项目创建/打开、格式验证、画布与页面、本地保存、资源恢复。
- Codex 通过 GitHub 插件查询仓库及处理 PR，通过本地 Git 准备本地检出、拉取、提交/推送；本地 Git 鉴权独立核对，不推断继承插件登录。
- Codex 调用搭建器的项目打开能力，把已准备好的目录交给搭建器；不必首版内置完整 GitHub 登录、仓库浏览和 Git 操作面板。
- 所有可视化编辑仍以本地工程文件为事实来源，不混用远端文件 API 独立修改同一项目造成两份状态。拉取后仍须重读与校验，依赖可移植性和过期写入保护仍需实现。

目前可行的是由 Codex 调度两端能力；没有验证搭建器 iframe 可直接调用另一插件的工具或继承其凭据，不能把此路径当作现成 SDK。上文 RepositoryService 是后续需要纯按钮闭环时的可选本地适配层，首版可优先用现有能力完成工作流。若用户要求完全不用 AI 的一键克隆/同步，再单独实现对应按钮和服务。
